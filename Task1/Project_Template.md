# Задание 1. Исследование моделей и инфраструктуры для RAG-бота

## Введение
Построения RAG-бота корпоративной базы знаний компании QuantumForge Software.

Компания работает с технической и архитектурной документацией, связанной с промышленными объектами и интеграциями со SCADA-системами. 
Это накладывает ограничения на обработку данных, требования к контролю инфраструктуры и воспроизводимости решения.
Необходимо обеспечить приемлемое качество ответов, масштабируемость с ростом базы знаний, как вариант, перевод на локальное развертывание при необходимости, простоту эксплуатации на этапе MVP.

## 1. Сравнение LLM-моделей

### 1.1 Локальные модели (Hugging Face)
**Качество ответов**
Современные open-source модели (Llama 3 8B/70B, Mistral 7B) демонстрируют достаточное качество для RAG-сценариев, где основная ценность — корректное извлечение и пересказ найденного контекста. В задачах строгих рассуждений и генерации сложных текстов уступают топ-облачным моделям, но для поиска по документации разница не так существена, на мой взгляд.
**Скорость**
На GPU — высокая и предсказуемая. На CPU с квантованием — приемлемая для внутренних инструментов и пилотных внедрений.
**Стоимость владения**
Требуют затрат на инфраструктуру (GPU, обслуживание). При регулярном использовании и большом числе запросов могут быть экономически выгоднее API-моделей.
**Развёртывание**
Требует экспертизы: управление моделями, памятью, квантованием. Возможна работа в изолированных средах и полный контроль над данными.
**Вывод**
Локальные LLM оправданы при строгих требованиях к конфиденциальности и долгосрочном использовании, но увеличивают сложность эксплуатации.

### 1.2 Облачные модели (OpenAI / YandexGPT)
**Качество ответов**
Облачные LLM демонстрируют стабильное качество, особенно в задачах суммаризации и объяснения. Хорошо подходят для RAG, где модель опирается на найденный контекст.
**Скорость**
Низкая латентность при обычных нагрузках. Зависимость от сети и внешнего сервиса.
**Стоимость**
Оплата за токены, при большом объеме может быть дорого. Для внутренних инструментов с умеренным числом пользователей — предсказуемые расходы.
**Развёртывание**
Минимальные усилия: API-ключ и HTTP-интеграция. Нет необходимости в собственной GPU-инфраструктуре.
**Вывод**
Облачные LLM — оптимальный выбор для MVP и учебного проекта при отсутствии жёстких регуляторных ограничений.

### 1.3 Выводы по LLM
LLM не является узким местом, так как основную точность определяет retrieval. Рационально начать с облачной модели для скорости внедрения, но как вариант возможно и локальное развертывание. Архитектура должна допускать последующую замену LLM на локальную без изменения остального пайплайна.

## 2. Сравнение моделей эмбеддингов

### 2.1 Локальные Sentence-Transformers
**Скорость индексации**
Высокая, особенно при использовании GPU. Отсутствие rate-limit’ов упрощает инкрементальные обновления.
**Качество поиска**
Модели уровня `all-MiniLM` или `bge-base` обеспечивают хорошее семантическое покрытие для технической документации.
**Стоимость**
Фиксированные инфраструктурные затраты. Отсутствие платы за объём данных и число запросов.
**Вывод**
Хорошо подходят для корпоративных баз знаний с регулярным обновлением.

### 2.2 Облачные эмбеддинги (OpenAI)
**Скорость**
Ограничения по rate-limit замедляют массовую индексацию. Подходят для небольших объёмов или нерегулярных обновлений.
**Качество**
Стабильное и предсказуемое. Универсальные модели без доменной адаптации.
**Стоимость**
Оплата за объём токенов. При росте базы знаний и частых переиндексациях стоимость увеличивается.
**Вывод**
Удобны для быстрых прототипов, но менее гибки для постоянно растущей базы.

### 2.3 Вывод по эмбеддингам
Предпочтительны локальные Sentence-Transformers, так как лучше контролируются, не зависят от API-ограничений и легко встраиваются в автоматическое обновление индекса.

## 3. Сравнение векторных баз данных

### 3.1 ChromaDB
**Преимущества**
Удобный API и встроенная работа с метаданными. Быстрое начало работы без тонкой настройки.

**Ограничения**
Более сложная эксплуатация при росте нагрузки. Дополнительные зависимости и сервисная логика.

### 3.2 FAISS
**Преимущества**
Высокая производительность поиска. Минимальное количество компонентов. Простота контейнеризации и воспроизводимости.

**Ограничения**
Нет встроенного хранилища метаданных (решается на уровне приложения). Не ориентирован на частые real-time обновления без пересборки.

### 3.3 Вывод по векторной БД
Для MVP:
* объём данных умеренный;
* высокая конкурентность не требуется;
* важна простота Docker-развёртывания и демонстрации.

**Рекомендуемая векторная БД: FAISS.**

## 4. Рекомендуемая конфигурация сервера

### Базовая конфигурация (MVP)

| Компонент | Конфигурация            |
| --------- | ----------------------- |
| CPU       | 8–16 vCPU               |
| RAM       | 32–64 ГБ                |
| GPU       | опционально (T4)        |
| Storage   | 300–500 ГБ SSD          |
| ОС        | Linux (Ubuntu LTS)      |
FAISS и эмбеддинги могут стабильно работать на CPU, GPU требуется только для ускорения.

## 5. Итоговые варианты архитектуры

### Вариант 1. Cloud LLM + локальные эмбеддинги + FAISS (рекомендуемый)
Быстрое внедрение. Минимальная инфраструктура. Простой и прозрачный RAG-пайплайн.

### Вариант 2. Полностью локальный стек
Максимальный контроль над данными. Более сложная эксплуатация. Подходит для зрелого продакшена.

### Вариант 3. Полностью облачное решение
Простое начало. Рост стоимости при масштабировании. Повышенные риски при работе с чувствительными данными.

## 6. Финальная рекомендация
Для задачи QuantumForge Software оптимальным является следующий стек:
* **LLM:** облачная модель (на этапе MVP) или если "знания" конфиденциальные лучше локальная модель;
* **Эмбеддинги:** Sentence-Transformers (локально);
* **Векторная БД:** FAISS;
* **Развёртывание:** Docker / Docker Compose с возможностью миграции в Kubernetes.
